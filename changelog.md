# Level 0 Engine Changelog

## [v1.1.9] - 2026-08-17

_Measuring The Chunk Builder, And Discovering It Was Never Building_

### Added

- **[TOOLING] Per-Phase Chunk Build Profiler (`ChunkManager._profBegin/_profAdd/_profEnd`):** v1.1.8 closed with two named suspects for the chunk phase — the unyielded quadratic breach-wall pass, and the `setTimeout(0)` slice budget — and a note saying to instrument before touching either. Instrumenting first was correct, because **both were wrong.** Every chunk build now records `worker` / `cells` / `breach` / `instances` / `shadow` / `warm` / `yielded` into `env.genStats.phases`, with a full copy of the single worst chunk retained in `genStats.worstProfile`. `yielded` is tracked separately from work so "this chunk is expensive" can be told apart from "this chunk yielded a lot and the scheduler was slow returning". Roughly ten `performance.now()` calls per chunk, so it stays on permanently. The first run settled the question immediately: of 3902ms across 9 chunks, **breach was 12ms (0.3%), cells 84ms, worker 16ms, instances 23ms, yielded 5ms — and shadow prewarm was 3735ms (96%)**. Both v1.1.8 hypotheses are formally withdrawn; neither was worth optimising.

### Changed

- **[GRAPHICS] Shader Warmup Compiles The Variants Materials Actually Use (`warmMaterialVariants`, `queueShadowPrewarm`, `_unwarmedMaterials`):** With the profiler pointing at `drainShadowPrewarm`, the question became why it cost so much. `plain`, `instanced` and `instanced + instanceColor` are three separate entries in both the visible and depth program cache keys, so the warmup compiled three programs per material — blind, because `ShaderWarmup` runs before any chunk exists and cannot know how a material will be used. Surveying a live scene showed how badly that guess paid: **328 distinct materials produced 984 compiled shadow variants of which only 352 were ever used — 64% waste — and no material was used in all three forms, while 304 of 328 were used in exactly one.** The split is lopsided rather than even: 317 materials appear as `plain`, 28 as `coloured`, 7 as `instanced`. Warming is now form-aware end to end. `_unwarmedMaterials` reads the real form off each object (`isInstancedMesh`, `instanceColor`) and returns a `Map<Material, Set<form>>`; `queueShadowPrewarm` stores `{material, form}` pairs; the probe rig lights only the probe matching the requested form; and the warm-state key includes the form, so warming a material as `plain` can never mask a later, genuinely-needed `coloured` warm — the failure mode that would have reintroduced a cold compile on first sight. `ShaderWarmup` blind-warms `plain` only, and defers the two instanced forms to the chunks that actually create them, where `_compileInstances` has already decided the answer and the drain still runs before `contentReady` is set. Measured end to end: **shadow prewarm 3735ms → 1805ms, chunk phase 3678ms → 2000ms, engine boot 6131ms → 4607ms (25% faster)**. `_programKeepAlive` also stops growing three clones per material, falling from 1043 entries to 659 after an identical boot.
- **[UI] Boot Phase Bands Re-Measured:** With the chunk phase down from 3678ms to 2000ms it no longer dominates — it now sits roughly level with the program link (1947ms). `BOOT_PHASES` re-weighted accordingly: CHUNKS 16-76% → 15-58%, SHADERS 76-99% → 58-99%, and the smaller phases nudged to match a 4607ms baseline.

### Fixed

- **[PERFORMANCE] Chunk Streaming's Blocking Shader Link, Verified:** v1.1.8 shipped this fix flagged as "verified structurally, not by frame timing" — the mechanism was read and corrected but never demonstrated. It has now been measured directly, by counting entries into the unbudgeted `_drainProgramLinks` path (the one that skips `KHR_parallel_shader_compile`'s completion check) across a fixed 12-chunk-step traversal building 36 fresh chunks. **With the fix: 0 blocking drains, 898 budgeted ones. With the pre-fix behaviour restored on the same build: 55 blocking drains.** The dangerous path is deterministically gone. Frame timing across the same traversal came out at worst frame 121ms, 2 frames over 100ms, 17 over 30ms, median 17ms — against 231ms / 2 / 24 / 19ms before the form-aware warming above, so streaming is no worse and probably better. See Known for why the frame numbers alone still cannot carry the claim.

### Known

- **[PERFORMANCE] Batching the shadow probe rig was tried and reverted.** Compiling 8 materials per `renderer.render()` instead of one moved total shadow prewarm only 3735ms → 3547ms, inside run-to-run noise. That is itself a useful result: it establishes the cost is the driver compiling each depth program (~4.7ms per program, ~750 programs) rather than per-render overhead worth amortising, which is what redirected the work toward compiling *fewer* programs instead of compiling them faster. It was reverted rather than kept because it also made the per-frame drain in `animate()` strictly worse — a batch cannot be interrupted, so its 2ms budget would only be checked after eight materials rather than one. The rig keeps its multi-slot structure with `SHADOW_PROBE_BATCH = 1`, and the constant carries the measurement.
- **[PERFORMANCE] The remaining 1805ms of shadow prewarm is real compile work, not waste.** With the 64% variant waste removed, what is left is roughly 350 depth programs that genuinely get used. It is paid behind the loading screen rather than during play, which is the correct place for it, and there is no further redundancy identified in it. Making it smaller now means compiling fewer materials, not compiling them more cleverly.
- **[PERFORMANCE] Traversal frame times still cannot be A/B'd cleanly in one session, exactly as v1.1.3 warned.** Running the pre-fix arm second produced *better* frames (worst 70ms) than the fixed arm running first (worst 231ms) — not because the old code was faster, but because the browser's persistent GPU program cache was warm by then and the blocking drains found everything already linked. Every frame-time figure in this entry is directionally useful and none of it is a controlled comparison. The blocking-drain *count* is the load-bearing evidence here precisely because it is immune to that confound. A cold-cache-per-trial harness remains unbuilt.
- **[PERFORMANCE] Chunk queue ordering, predictive prefetch and worker pipelining are all closed as not worth doing.** Each was a v1.1.8 candidate; the profiler priced them at 16ms (worker), 84ms (cells) and 23ms (instances) across nine chunks combined. There is no meaningful time in chunk *generation* — the phase was never building geometry, it was compiling shaders.
- **[SYSTEM] `_programKeepAlive` still grows without bound**, just three times slower. Form-aware warming means one clone per material-form rather than three per material, but nothing releases them, and `_forgetMaterialPrograms` still clears the warm-state keys on chunk disposal so a re-created identical material re-warms and appends again. Unchanged in kind from v1.1.8.

## [v1.1.8] - 2026-08-17

_Boot Told The Truth, And The Truth Was Somewhere Else_

### Fixed

- **[ASSETS] The Static Texture Pipeline Was Silently Corrupting Two Materials:** Found while extending the exporter to cover per-sector bundles, not while looking for it. `assets/export_textures.html` recorded a fixed list of scalar properties per material and had no notion of material *kind*, so `StaticTextureLoader` rebuilt everything it loaded as a `MeshStandardMaterial`. Two assets did not survive that round trip. `flareMat` is a `THREE.SpriteMaterial` — `ImpoundSector.js:151` does `new THREE.Sprite(env.flareMat.clone())`, and a `Sprite` cannot render with a mesh material at all, so every impound flare had been drawing with the wrong material class since the static pipeline landed. `glowMat` lost `blending: THREE.AdditiveBlending` and its `polygonOffset`/`polygonOffsetFactor` pair, because the metadata schema never had fields for them — every additive glow in the static set was coming back as ordinary alpha blending with its depth offset gone. Neither failed loudly; both simply looked slightly wrong forever. The schema now carries `blending`, `polygonOffset`, `polygonOffsetFactor`, `side`, `depthWrite`, `alphaTest`, `vertexColors`, plain-data `userData`, and an explicit material kind (`Material` / `BasicMaterial` / `SpriteMaterial`), and the loader reconstructs each accordingly. Verified off the running engine after a re-export: `flareMat.isSpriteMaterial === true` with `blending === 2` (`THREE.AdditiveBlending`) and its map attached, `glowMat.blending === 2` with `polygonOffset === true`. Metadata and disk now agree exactly — 169 expected, 169 present, zero orphans, zero missing.
- **[PERFORMANCE] Chunk Streaming Blocked On Shader Links Mid-Build:** `ChunkManager.warmChunkMaterials` runs at every yield point inside a chunk build — roughly every 5ms of generation — and reached `warmMaterialVariants` and `_scopedCompile` on their old `drainNow = true` defaults. That path calls `_drainProgramLinks()` with no budget, and the polling guard is written as `polling = ext !== null && budgetMs !== Infinity`, so the unbudgeted call **skips the `KHR_parallel_shader_compile` completion check entirely** and calls `getUniforms()` on every pending program regardless of whether the driver has finished linking it. The v1.1.3 work removed exactly this stall from the boot warmup but left it in place on the per-chunk path, where it fired far more often. It only ever bit on first traversal into fresh geometry, because `_warmedMaterials` suppresses the warm on every subsequent visit — which is precisely the "mild stuttering when first traversing" shape reported. `warmChunkMaterials` now passes `drainNow: false`, and the default on both `warmMaterialVariants` and `_scopedCompile` was flipped to `false` so a blocking drain is a deliberate opt-in rather than something a caller inherits by omission. The per-frame `drainProgramLinks(1.5)` in `animate()` collects the results through the polling path that was always there for it.
- **[UI] Boot Phase Counter Ran Backwards:** `Environment.setup()` advanced the sequence to phase 4, then `main.js` re-announced phase 3 immediately afterward. The badge displayed `PHASE 03/06` after phase 4 had already run, and `phaseDurations` accumulated a duplicate, meaningless phase-3 row that landed in the end-of-boot `console.table`. The stale call is gone. Verified by sampling the live overlay every 100ms across a full boot: **zero backward steps**, monotonic to 100%.
- **[UI] In-Game Sector Loads Displayed A Frozen 100% Bar:** Every sector transition called `setPhase(3, 'LOADING ANOMALOUS SECTOR...', 50)` on the already-finished boot controller. That could not work by construction — `targetProgress` only ever moves through `Math.max`, so it was still pinned at 100 from the end of boot, and `_onFrame`'s `requestAnimationFrame` loop had already exited on completion, so nothing was animating anyway. Players saw a stale `PHASE 03/06` badge over a full bar reading `[ 100% ]` on every transition. Replaced with a real state teardown (`beginSubLoad` / `endSubLoad`) rather than a reuse of the boot phase machinery: progress resets, the rAF loop restarts, the badge reads `SECTOR LOAD` instead of a fabricated phase number, the minimum-duration gate is bypassed, and a synthetic crawl carries the bar because the chunk builder genuinely cannot report meaningful progress mid-transition. `endSubLoad` stops the loop again so the overlay is not left spinning for the rest of the session.
- **[TOOLING] Reported Boot Time Excluded Most Of Boot:** `BootController.startTime` is set inside `init()`, which runs after the browser has parsed the HTML, fetched and evaluated `r160.js`, and walked the entire 122-module ES graph — and after the Continue prompt has been answered. `[BOOT] Complete in Xms` therefore quoted engine-phase time as if it were total boot, understating it, while folding it all together would instead blame the engine for however long a player sat deliberating at the Continue screen. `main.js` now captures a mark before the prompt and another after it, and `finish()` prints a three-way `console.table` — document + modules, Continue prompt (user-gated), engine phases — plus the total. Measured on the reference machine: **182ms pre-engine, 4740ms at the prompt, 6131ms of engine boot**. The prompt time is real and was previously invisible; it is now impossible to mistake for engine cost.

### Changed

- **[SYSTEM] HTTP Caching Replaces `Cache-Control: no-store` (`engine_server.js`):** The dev server sent `no-store` on every response, so each boot re-downloaded `r160.js` (1.3MB), all 122 ES modules (1.3MB) and the entire texture set — which is almost certainly why the IndexedDB texture cache exists at all: it was working around a header the server itself was setting. Two lanes now. Content versioned by its own filename and never edited in place (`r160.js`, `assets/fonts/`) gets `public, max-age=31536000, immutable`. Everything else — source modules, HTML, and the texture WebPs, which *are* rewritten whenever the exporter re-runs — gets `no-cache` plus a weak `ETag` built from size and mtime, so the browser keeps the body but revalidates and receives a bodiless 304 when nothing changed. `immutable` was deliberately not used for `assets/textures/`: a stale WebP served mid-export-iteration would be a miserable bug to chase, and revalidation captures nearly all of the win without that risk. Measured on a warm reload: `r160.js` **0 bytes transferred** against 1,316,151 decoded, `vt323-latin.woff2` **0 bytes**, and a representative module (`Environment.js`) **300 bytes** against 30,965 decoded. The success branch also had to be restored — an in-flight edit to remove the `no-store` header had deleted the entire `else` arm, leaving every successful request with no response written at all. `PORT` now honours `process.env.PORT`.
- **[NARRATIVE] Case Data Loads In Parallel:** `StoryEngine.loadData` awaited seven `fetch` calls inside a `for` loop — seven sequential round trips for 128KB. Now a single `Promise.all`; per-file progress still reports as each individually lands, just in completion order rather than declaration order. An `res.ok` check was added, since failures were previously swallowed into a generic catch and reported as nothing at all.
- **[ASSETS] Texture Loading: One IndexedDB Transaction, Off-Thread Decode, No Leaked Object URLs:** `StaticTextureLoader` called `TextureCache.getBlob` per texture, and each call opened its own readonly transaction — roughly 95 separate open/commit cycles during the busiest stretch of boot. Added `TextureCache.getAllBlobs()` (`getAllKeys` + `getAll` on one transaction) and `saveBlobs()` for the write side, and the loader now primes once and resolves everything against that map. Decoding moved from `THREE.TextureLoader` — which goes through an `<img>` element and decodes on the main thread — to `createImageBitmap`, which decodes off it; this also removes object URLs from the path entirely, so the ~95 `URL.createObjectURL` calls that were never revoked no longer exist to leak. `imageOrientation: 'flipY'` paired with `texture.flipY = false` reproduces the old upload orientation exactly, and that was verified rather than assumed: sampling 5,476 points of `wallTexture` against a raw decode gives a **100% mirror match and 16% identity match**, confirming the browser honours the orientation hint. `THREE.TextureLoader` remains as an automatic fallback, now with proper revocation.
- **[ASSETS] Six Of Eight Sector Texture Bundles Are Now Static:** `lazyLoadSectorAssets` synthesised all eight per-sector bundles on the CPU every boot even though `USE_STATIC_TEXTURES` was already true for the 57-entry core set. Each bundle is now tried against the exported static set first and only generated on a miss. The exporter classifies every asset it encounters and records anything it cannot represent as a `residual`; a sector with a non-empty residual list is skipped wholesale rather than partially reconstructed, because half-static/half-generated would leave cross-referenced assets dangling. Result: **ANNEX, IMPOUND, BOARDROOM, ATRIUM, CHECKPOINT and INCINERATOR load statically; MAINTENANCE and ARCHIVE stay on the generator** (see Known). Bundle time fell **218ms → 120ms**, and the win landed where it mattered — INCINERATOR **101ms → 26ms**, CHECKPOINT **44ms → 17ms** — while the two sectors that stayed procedural were already 1-2ms each. `ProceduralTextureFactory.sectorGenerators()` is now the single source of truth shared by the runtime fallback and the exporter, so adding a sector reaches both.
- **[TOOLING] Exporter Emits WebP Directly:** The exporter wrote PNGs and the loader fetched `.webp`, with an undocumented manual conversion step in between that no longer had to exist. It now calls `canvas.toDataURL('image/webp', 0.92)` and the server derives the file extension from the data URL's declared MIME type, so output format is chosen in exactly one place. Export endpoints are origin-relative rather than hardcoded to `localhost:8080`. Full set: **169 files, 5.1MB** (was 95 files / 3.5MB — the growth is the newly-covered sector bundles).
- **[UI] Boot Progress Reweighted From Measurement, Not Intuition (`BOOT_PHASES`):** The old milestones (15/40/65/70/85/98) were hardcoded across three files and bore no relation to cost — the two cheapest steps owned 40% of the bar. Percentage bands now live in one exported table in `BootController`, and every call site reports a 0..1 fraction of its own step via `setPhaseProgress`; no other file hardcodes a boot percentage. Bands are sized from a measured 6131ms boot: DATA 365ms (0-6%), ASSETS 177ms (6-9%), GRID 2ms (9-10%), BLUEPRNT 355ms (10-16%), **CHUNKS 3678ms (16-76%)**, SHADERS 1553ms (76-99%), STABLE 1ms (99-100%). Reweighting is now a one-line edit against the console table the controller already prints.
- **[UI] Boot Shader Compile Sliced, With A Crawl Underneath:** `renderer.compileAsync(scene, camera)` over the whole scene measured **1075ms** and reports nothing while it runs, so the bar parked at its ceiling for over a second — the worst "is it frozen?" moment in the sequence. It now compiles a few top-level groups at a time by swapping `scene.children` (lights and cameras stay resident in every slice, since materials must compile against the lighting they will actually render with), with an asymptotic synthetic crawl covering each individually-opaque slice. Slice count matters far more than expected and was measured, not guessed: **1 slice → 1075ms, 3 slices → 938ms, 27 slices → 4853ms.** A few coarse slices cost nothing and give the bar real checkpoints; fine slicing is badly superlinear. `COMPILE_SLICES = 3`.
- **[UI] Boot Overlay Stopped Forcing Layout Every Frame:** `updateDOM` runs on every animation frame and unconditionally rewrote the log box via `innerHTML` — an HTML parse — then read `scrollHeight`, forcing a synchronous reflow, roughly sixty times a second for the whole of boot, competing with the very work it was reporting on. Element lookups are now cached, each field is guarded by a change check, and the log box is rebuilt from DOM nodes only when its contents actually change.

### Added

- **[UI] Self-Hosted VT323 (`assets/fonts/`):** `engine.html` loaded its only typeface from `fonts.googleapis.com` via a render-blocking stylesheet, which meant the boot loading screen itself could not paint until a third-party host answered — a hard dependency on external network availability before the engine could show that it was doing anything. Both latin subsets are now served from this origin (34KB total, SIL Open Font License 1.1), with the `@font-face` rules inlined directly into `engine.html` rather than linked, so the boot-critical path has zero render-blocking stylesheet round trips of any kind, and a `preload` hint starts the woff2 fetch before CSS-to-glyph matching would. `splash.html`, `index.html` and `readme.html` share `assets/fonts/vt323.css`; those three still reach Google for **Space Mono**, which is unchanged. Unicode ranges are copied verbatim from the Google Fonts CSS API so glyph coverage and per-range loading behave identically. Verified live: `document.fonts.check('16px VT323') === true`.
- **[SYSTEM] Module Preload Hints (`tools/gen-modulepreload.js`):** `main.js` reaches 121 further modules at a graph depth of 5, so without hints the browser can only discover each level after parsing the one above it — five sequential round-trip generations spent merely finding out what to fetch, with HTTP/1.1's six-connection limit making the tail of each generation block the start of the next. All 121 are now declared `rel="modulepreload"`, placed *after* the `r160.js` tag so three.js keeps first claim on the connection pool (nothing can run without the global `THREE` it defines). The list is generated from the real import graph rather than maintained by hand, breadth-first so emission order matches load order, and rewritten in place between markers — run `node tools/gen-modulepreload.js` after changing any import.
- **[UI] The Initial Chunk Build Has A Phase:** The single largest stretch of boot — **3678ms of 6131ms, sixty percent** — ran inside a bare `await` in `main.js` with no reporting whatsoever, freezing the bar mid-sweep for seconds. This was missed in the original audit and only surfaced once end-to-end phase timing existed to expose the gap. It now owns the `CHUNKS` phase and reports against `genStats.count` versus the chunk count the streamer is targeting, with flavour lines firing every 1.8s so long stalls on slower hardware still read as alive.

### Known

- **[ASSETS] MAINTENANCE and ARCHIVE will stay on the generator permanently, by design.** Both return assets a texture pipeline cannot represent: `leakStainGeo`, `paperGeo` and `coffeeStainGeo` are `BufferGeometry`; `bookMatSets` is an array of arrays that shares `pageMat` by reference across every entry, so exporting it would silently de-alias into distinct copies; and `archiveWallMat.userData` points at its own baseboard and trim materials, a cross-reference with nowhere to live in a flat metadata file. The exporter reports each of these by name and reason on every run rather than skipping them quietly. Both sectors generate in 1-2ms, so nothing meaningful is lost.
- **[PERFORMANCE] The in-world stutter fix is verified structurally, not by frame timing.** The blocking-drain path was confirmed by reading it, and the change is verified not to have broken boot, but **no traversal frame-time measurement was taken before or after** — the session's verification was all boot-side. The v1.1.3 notes are explicit that run-to-run variance on this class of stall can be as large as the effect being measured, so this should be treated as an understood mechanism corrected, not a demonstrated improvement, until a fixed-seed fixed-traversal benchmark runs against it.
- **[PERFORMANCE] The chunk phase is one chunk, not nine.** Final measurement: 9 chunks, 3823ms total, **worst single chunk 2186ms** — 57% of the phase in one build. Nearest-first queue ordering and predictive prefetch, both previously identified as candidates, address distribution rather than this. The unyielded quadratic breach-wall pass in `_buildChunkInterior` (allocating `[...chunkGroup.children, ...stagingMeshes]` per breach wall, `Array.includes` inside its inner loop, and a `fixtureData.filter` that reclones a bounding box per fixture per wall, with no yield anywhere in the block) is the more likely candidate. Instrument inside `_buildChunkInterior` before touching any of it.
- **[ASSETS] The off-thread decode depends on `imageOrientation: 'flipY'` being honoured.** Verified true on this browser. Any environment that accepts the option but ignores it would render every static texture vertically mirrored while reporting no error — the `THREE.TextureLoader` fallback only engages when `createImageBitmap` is absent or throws, not when it silently misbehaves. The mirror-match assertion used to verify this is worth keeping as a startup check if the engine ever ships to a wider browser matrix.
- **[SYSTEM] `_programKeepAlive` still grows without bound.** `warmMaterialVariants` pushes three material clones per warmed material and never releases them, while `_forgetMaterialPrograms` removes the entry from `_warmedMaterials` on chunk disposal — so a re-created identical material is re-warmed and adds three *more* clones. Unrelated to this pass's changes and unchanged by them, but it accumulates across a long traversal session.

## [v1.1.7] - 2026-08-17

_A Fixed Light Budget, and Arches That Curve_

### Fixed

- **[GRAPHICS] Arch Curves Read As Flat Segments:** The curved span of every archway showed its tessellation, each segment catching the light at its own angle and reading as if the arch were casting shadows onto itself. Nothing was occluding anything — `THREE.ExtrudeGeometry` returns a non-indexed mesh, so the `computeVertexNormals()` call in `StructureKit.buildArchCutout` gave every wall quad along the intrados a single flat face normal, and the curve was genuinely flat-shaded. Vertices lying on the arc's swept cylinder now take the analytic radial normal instead, with the sign lifted from the flat normal so the fix stays independent of the shape's winding; adjacent quads agree at their shared edge and the curve shades as one surface. Everything else — the extrusion caps, the outer box faces, the jambs — keeps its flat normal, so the hard edges stay hard. `curveSegments` also raised 24 → 32 for the silhouette. Both `CURVED ARCHWAY` and the Arch Halls share the builder and get it. Verified against the live geometry (`archCutout_1.2_0.8_1.5_4_1.5`): all 378 intrados vertices exactly radial, max deviation from the analytic normal `2.9e-8`, all facing inward consistently, and 63 distinct normals across the arc — one per ring position, shared between neighbouring quads, which is the smooth-shading signature.
- **[PERFORMANCE] Hard Stutter On Picking Up Tapes, Laptops and Notes:** Reported as a hitch on first reading a note or picking up a tape recorder, most noticeable on tapes and laptops. Not the document overlay, the story fragment or the foley — measured at 0.5ms for the entire `somatic-read` handler. Every one of these props carried its own `PointLight` child for its glow, and `WebGLRenderer.projectObject` returns early on any object whose `visible` is false, so `hit.visible = false` on pickup hid the light along with the mesh. That drops `NUM_POINT_LIGHTS`, which is part of every material's shader program cache key, and the entire visible set has to relink synchronously in the frame the player pressed E. Measured against a live 40-point-light scene: **26 new programs and ~72ms of compile for a single light appearing or disappearing**. It only bit the first time a given light count came up, since the programs are cached afterwards — which is why it read as "the first tape, the first laptop" rather than every pickup. Fixed structurally by pooling the glows (below); the pickup path now calls `releasePropLighting()`, which retires the prop's fixture and — belt and braces for anything that still parents a real light to a prop — re-homes stray lights onto the chunk group at zero intensity rather than letting them wink out with the mesh. Re-measured through the real placement path: **0 new programs on pickup, 0.1ms to release**.

### Changed

- **[GRAPHICS] Prop Glows Run Through The Light Pool (`PropGlow.js`):** Notes, documents, tapes, laptops, clipboards and the Atrium vending fronts each used to own a dedicated `PointLight`, which put a variable number of real lights in the scene — one per prop in every loaded chunk. Because the light count is baked into every material's program key, chunk loads, chunk unloads and pickups all moved it, and each move cost the relink measured above. A prop glow is now a LumenGrid fixture competing for the same fixed pool of 32 lights as every ceiling panel and lamp in the level, via `attachPropGlow()`; nine light sites were converted across `NarrativeProps.js` (six), `AnnexSector.js` (two) and `AtriumSector.js` (one), with per-prop colour, intensity, reach and local offset kept in one `PROP_GLOW` table so each reads exactly as it did. Three hooks were added to `LumenGrid` to carry them: `fixture.color`, since pool lights are recycled between fixtures and a prop glow has no emissive material to read its colour from; `fixture.slotBias` (+40 in distance-squared units, roughly "pretend it is 6m further away"), because a glow centimetres from the player's face would otherwise evict every room fixture around it and leave the room dark behind the note; and `fixture.noGlare`, because glare and pupil adaptation track the nearest fixture and these glows were not fixtures at all before. Fixtures declare the intensity they want the pooled light to end at, so `attachPropGlow` divides out the pool's 0.35 non-shadow slot scalar. Verified by placing a note through the real `placeEphemera` path: the pooled light comes out white at intensity **1.201** against the old raw light's 1.2, distance 3.0, position identical, landing in slot 6 — the first non-shadow slot, so a note on the floor never takes a shadow map. Scene census afterwards: 32 pooled point and 32 pooled spot lights, and **zero lights owned by a streamed chunk**. The 8 point and 3 spot lights outside the pool are the entity and player rigs, built once at boot; each entity's `deactivate()` leaves its group visible, so those never move the count either. The engine's light count is now constant for the whole session.
- **[UI] Virtual Cursor Hit-Testing Deferred To A Frame:** `SomaticInput._onMouseMove` hid `#virtual-cursor`, called `elementFromPoint`, then restored it — two synchronous style and layout flushes per event, and under pointer lock a high-polling mouse delivers mousemove far faster than the frame rate, so a document left open was paying hundreds of forced layouts a second. The hide was redundant to begin with: the cursor is already `pointer-events: none` and was never the hit result. The hover probe now runs once per frame through `_queueHoverProbe()` and clears its stale `.virtual-hover` when reading ends. The gamepad cursor path shares it.

### Known

- **[GRAPHICS] Prop glows now compete for the 32 pool slots, and can lose.** Two intentional consequences of pooling: a glow fades in over the pool's standard 0.6s spawn ramp as it comes into range rather than being lit the instant its chunk loads, and where 32 lights are already claimed nearby a distant prop may not light until the player approaches. `PROP_GLOW_SLOT_BIAS` in `PropGlow.js` is the knob if the balance reads wrong in play.
- **[GRAPHICS] This pass was verified against the live scene graph and renderer, not on screen.** Program counts, compile costs, the arch's normals and the resulting pooled light were all read off the running engine, which exercises the real code paths, but the preview surface could not composite frames during the session so nothing here has been eyeballed in motion.

_Closing the Warmup Gap and Watching the Boot Sequence Work_

### Fixed

- **[WORLD] Missing Crawlspace Covers:** Fixed a logic error inside `StructureKit.js` where overlapping cell placements were mistakenly deleting existing grates instead of preserving them. Crawlspaces and vents will no longer sporadically spawn missing their hatches and covers.
- **[SYSTEM] Boot Sequence Crash on `helpers.boxGeo`:** Fixed a runtime `TypeError` halting the `ChunkManager` during boot. A minor local scope issue while implementing the new doorknobs caused `addGrate` to check `helpers.boxGeo` instead of the instantiated `this.boxGeo`. Blueprints generating anomalous and hinged doors were also updated to properly reference the doorknob builder from their local context to prevent silently failing to attach handles.
- **[PERFORMANCE] Shader Warmup Missed Every Per-Sector Material:** A player reported the engine freezing for a couple of seconds while reading a laptop note in the Annex — right before the note itself appeared, matching the synchronous shader-compile stall class from v1.1.3 rather than anything specific to reading documents. ## [v1.1.3] - 2026-08-16

_Warming the Shader Programs the Engine Actually Uses_

### Added

- **[GRAPHICS] Shadow-Depth Program Prewarm (`ChunkManager.queueShadowPrewarm`, `drainShadowPrewarm`):** Added a queue of materials awaiting their shadow-pass programs, fed from `warmMaterialVariants` so it catches both the boot warmup and every chunk build, and drained two ways. A 2ms slice runs in `animate()` immediately after `engine.render()`, so a compile lands in the gap between frames rather than inside one. A second bounded drain runs at the tail of `_buildChunkInterior`, where the chunk's own new materials can be retired while the chunk is still invisible and the build is already yielding — a chunk can otherwise mint a material and put it on screen in the same frame, outrunning the per-frame drain. The probe rig renders the **real** materials rather than clones, against two throwaway shadow-casting lights into a 4x4 target: a depth program's cache key does not depend on light counts, so two scratch lights produce exactly the programs the real fixtures need, and borrowing the live fixtures would leave their shadow maps holding a picture of a probe plane. Using originals also keeps this path out of `_programKeepAlive`. Three probe meshes per material — plain, instanced, and instanced with `instanceColor` set, since `instancingColor` is in the depth program's cache key as well as the visible one.

### Changed

- **[GRAPHICS] Shader Link Draining No Longer Blocks:** `_drainProgramLinks` called `getUniforms()` on every program after every warmup batch. That call blocks until the driver finishes linking, which is the point of it — but waiting per batch meant the driver linked eight materials while nothing else was submitted, serialising `KHR_parallel_shader_compile` into exactly the sequential link the r160 upgrade was made to escape, and re-waiting on programs already drained dozens of times over. Measured at boot: **7,126ms in the drain against 89ms of actual `renderer.compile()`**. Each program is now drained once, tracked in a `WeakSet`, and the boot warmup queues every compile without waiting on any of them. Completed links are collected a slice per frame in `animate()`, using the extension's `COMPLETION_STATUS_KHR` to skip programs still in flight rather than stalling on them. The material warmup phase fell from **7,270ms to 125ms**.

### Fixed

- **[GRAPHICS] Multi-Second Stalls On Reaching New Geography:** Streaming into unseen chunks could stop the engine dead for seconds at a time. Measured on a live build, a traversal requiring 26 new shader programs cost a single **2,764ms frame**, while one requiring 2 had a worst frame of 28ms — the stall is synchronous shader compilation, and it scales with how many programs are new. The cause is a structural gap in the warmup rather than a shortfall in it. Three builds a material's `depth` and `distanceRGBA` programs inside the shadow pass, and `_scopedCompile` calls `renderer.compile()`, which never runs that pass; `warmMaterialVariants` compounds it by never setting `castShadow` on its probes. Neither fix works alone. So the boot warmup spent roughly ten seconds compiling 558 material clones into 107 programs, of which only 11 were shadow programs, and the remaining 43 shadow programs compiled during play — one stall per corner turned. Counted directly off the renderer: **107 programs after boot against 209 after a few minutes of walking**, with 80% of the shadow programs arriving during gameplay. With the prewarm in place, shadow programs stand at 48 to 60 before the player moves, and across six aggressive traversals the **worst frame fell from 2,764ms to 231ms**, four of the six running clean at a steady 60fps with a worst frame of 23 to 30ms. Boot is unchanged at 14.8s, since the queue is drained during play rather than folded into startup.
- **[GRAPHICS] Renderer State Restored Around Probe Renders:** The prewarm renders into its own target with its own lights and its own scene graph. Render target, `shadowMap.enabled` and `shadowMap.autoUpdate` are captured and restored in a `finally`, and `scene.children` is swapped back regardless of outcome, so a failed probe cannot leave the renderer pointed at a 4x4 buffer. Verified live after a full session: render target back to `null`, probe rig absent from the scene graph, all 14 shadow-casting lights intact.

### Known

- **[GRAPHICS] Stalls are reduced, not eliminated, and further tuning is now below the measurement noise floor.** On a purged ANGLE program cache (AMD Radeon RX 7800 XT) the worst frame across five traversals sits around **400 to 435ms**, against a **2,764ms** baseline, with 11 to 25 programs still compiling during play. Those two figures are a range rather than a result: repeated runs of *identical* code produced 13 late / 435ms and 25 late / 399ms, so run-to-run variance is as large as the differences between the candidate fixes. Three further attempts were made and none survived measurement — a UV-less probe geometry (no better than noise), warming each chunk's real geometry-material-instancing combinations before the chunk becomes visible (worse: 592ms, and the warming work became the stall), and splitting the probe render per variant (worse). All three were reverted. The remaining late programs each differ from an already-warmed one by a single boolean field in the program cache key, so the mechanism is understood and the coverage is incomplete. Closing them needs a repeatable benchmark first — fixed seed, fixed traversal, cold cache per trial, several trials — because at this point the instrument cannot resolve the effect.
- **[GRAPHICS] Compiled shaders cannot be cached by the engine.** WebGL exposes no program-binary API — `getProgramBinary` is undefined and no binary extension is offered — so there is no way to persist compiled programs to IndexedDB alongside the texture cache. The browser's own on-disk program cache is the only reuse across reloads, and it is already doing its job: a genuinely cold first boot runs about 20s against 14 to 15s on every boot after. `TextureCache` purging does not touch it.

- **[GRAPHICS] Boot is unchanged at roughly 15 seconds, and cutting 7.1s out of the warmup did not move it.** The blocking drain was never on the critical path — it overlapped the initial chunk build, so removing it finished the chunk phase around six seconds earlier and the first full `engine.render()` simply absorbed the difference, since the links it no longer had to wait for it now waits for itself. Measured end to end on the live build: **0.2s** material warmup, **8.7s** initial chunk building, **1.1s** `compileAsync`, **5.5s** in the first `engine.render()`, **1.2s** of boot-bar animation and fade. There is no waste left in that sequence to delete; it is real work that happens before the threshold opens. Making boot shorter now means opening the threshold before all of it is finished, which is a design decision about how much first-minute stutter is acceptable, not a defect to fix.

- **[GRAPHICS] Three frames over 100ms survive across 27 seconds of streaming.** These are materials created and shown inside the same build, where even the pre-visibility drain has no runway. The test that produces them teleports six chunks at a time; a walking player gives the builder considerably more warning.
- **[GRAPHICS] `_programKeepAlive` grows unbounded at three clones per unique material,** reaching 1,062 in a single session. It belongs to the original `warmMaterialVariants` path, not the shadow prewarm, and is memory rather than framerate.

All eight legs now match the tables. `woodMat` is a shared material so there's no extra draw call. The checkpoint bench and the clinic waiting bench were left alone: the first is concrete-on-metal by design and the second was already an all-metal frame with vinyl pads.
- **[WORLD] The Crawlspace Marks Itself With Trim, Not Tape:** The low-clearance corridor cell signalled its dropped soffit with a flat `0xffdd00` stripe floating in the opening near the top edge, which read as a warning decal stuck onto a bug rather than a finished edge. The soffit's bottom edge is where the wall stops, so it now gets the same baseboard the walls get where they stop at the floor — body from 1.2 to 1.3875 in `env.baseboardMat`, trim capping it to 1.4109, both lifted from `addGeometry`'s baseboard so it's the identical profile at the identical 0.03 protrusion. The floor plainly carries on underneath; you just have to go down to follow it. Hazard tape is now gone from the engine entirely.
- **[WORLD] The Breach Grate Is Shut, And Swings:** The lattice grate in a wall breach was baked in at `rotation.y = Math.PI * 0.42`, permanently ajar, and wasn't an interactable at all despite the engine already having a full grate contract — `type: 'grate'`, `active: true` blocks, `E` sets it false and `InteractionController` swings it open and empties its collider. It now uses that contract. It has to be openable rather than a fixed pane because breach cells are what `forcedOpen` carves to guarantee connectivity, and a permanently sealed one would dead-end a route the pathfinder assumed was walkable. The default open animation rotates the mesh about its own centre and sinks it to y 0.05, which for a panel mounted flush in a wall drives it straight through that wall, so `addGrate` gained a `hinged` mode that hangs the panel off an edge pivot and rotates `pivot.rotation.y` instead. All nine existing vent-grate callers pass four arguments and keep the fall-flat path untouched.
- **[WORLD] The Rubble Breach Variant Is Gone:** The third `WallBreach` type — two canted pillars under a sagging extruded header — has been removed along with `buildSaggingHeader`, its only consumer. Its 30% share is handed to the two survivors in the 0.4 : 0.3 ratio they already had (`FRAME_CUTOFF = 3/7`, measured at 0.5719 / 0.4281 over 2M samples), so breaches stay as frequent as before and only the mix within them changes.
- **[AESTHETICS] Extruded Curves Halved Their Segment Count:** `buildArchCutout`, `buildCurvedCornerBlock` and `curvedFlatGeo` dropped from `curveSegments: 16` to `8`. Their UV math is angle-based rather than segment-indexed, so it's unaffected by the count. See the note below on why this is a polish change and not the performance fix it might look like.
- **[TOOLING] The Insert-Var Toolbar Is One Dropdown:** "Insert Core Var" (a hardcoded `['P','hours','pen','year']`) and "Insert Custom Var" (`paramsData.VARS`) have merged into a single "Insert Var" list covering built-ins and both stores, deduplicated, each showing what it currently resolves to. From inside a document there is no difference worth surfacing — every one of them is a token that resolves to a value — and the split only made the author work out which menu a name lived under before they could insert it. "Insert Role" stays separate.
- **[NARRATIVE] The Redundant Alias Vars Are Deleted:** `PEN` → `ctx.pen`, `EPOCH` → `ctx.siteYear` and `HOUR` → `ctx.hours` existed so a document could write `${PEN}` and match the thread name it was delivering. A count across `lore.json`, `clues.json`, `foreshadow.json`, `finales.json`, `threads.json` and `puzzles.json` found all three used exactly zero times — the documents write `${pen}` (4×), `${year}` (3×) and `${hours}` (1×) instead. Removing them costs nothing and clears three of the five collisions between thread names and variable names. `CIPHER` is kept deliberately: it resolves to the fully-solved access code and must never appear in visible text, but it's wanted for a future easy-mode puzzle that hands the player the answer outright.

### Fixed

- **[WORLD] Baseboards Stopped Growing Inside Special Sectors:** A change to baseboard generation left sector perimeter walls unprotected. `buildWall` gates the baseboard tag on material (`mat === env.sharedWallMat && yOffset === 0`), but `buildPerimeter`'s `pushWallSegment` set `baseboardFootprint` unconditionally, so every sector's perimeter got hallway trim regardless of what it was made of — visible as a yellow-cream baseboard running along the Archive's green wainscoting. Perimeter walls are two-sided, though: outward faces are `sharedWallMat` facing the hallway, inward faces are the sector's own material, and the baseboard is a single box wrapping the whole footprint. Gating on material alone removed it from the hallway side too, breaking the run where a corridor passes an overridden sector. The baseboard now carries per-face material arrays mirroring `multiMat`'s outward/inward logic, so the hallway keeps its continuous run and the interior faces render in the sector's own material.
- **[WORLD] Nothing Blocks An Airlock Approach:** `ChunkManager` already cleared a 3×4 apron in front of every airlock, but only in the wall grid — `setWall(false)` plus `forceStructure(null)`. Once a cell is non-wall it falls through to `_buildEmptyCell`, which has its own spawner, and that rolls a 20% chance of a floor-to-ceiling divider wall. Arteries were exempt; airlock aprons weren't, so a divider could plant itself squarely in the approach the compass is pointing down. The apron calculation is now extracted to `_airlockApron()` — verified behaviour-identical to the inlined version across 33,136 combinations of position, orientation and `outSign` — and shared between the grid clearance and a new `_isAirlockApron()` check that suppresses the divider and its attached chair. Ceiling panels and breakers are untouched so the approach keeps its lighting.
- **[WORLD] The Breach Sill No Longer Stands Proud Of Its Own Wall:** Routing the crawl breach's sill through `buildWall` to give it a baseboard introduced a visible lip: `buildWall` inflates every piece by 0.02 and the jambs and header above were still raw `BoxGeometry`. It also rescales V by `h/3` offset by `yOffset/3`, so the wallpaper tiled at a different frequency above the lip than below it. All three pieces now go through `buildWall` with the correct `yOffset`, giving a continuous V run of 0 → 0.2 → 1.0 and a uniform 0.333 v-units per world unit across the whole wall.
- **[WORLD] Grate Edges Stopped Z-Fighting Their Own Opening:** The closed panel sat 0.02 from the header underside and the sill top, close enough for the depth buffer to argue. Clearance is now 0.06 per edge — a 1.08 square in a 1.2 opening, 0.05 clear on all four sides once `buildWall`'s inflation is accounted for.
- **[NARRATIVE] A Sighting Report Was Printing Its Own Template Token:** `lore.json`'s Chasm sighting report signed off `-${c.lead]` — a closing bracket instead of a brace. The token never closes, so `replaceTemplates` never matched it and the document has been rendering the literal string `-${c.lead]` to the player instead of the lead's name.
- **[TOOLING] Data Validation Catches A Wrong Closing Bracket:** `findTypoTokens` checked for `$(name}` and for a missing `$`, but nothing checked the *closing* side, which is exactly how the malformed token above shipped. It now also flags `]` and `)` closes, verified not to false-positive on valid tokens.

### Notes

- **The curved archways were not the performance problem, and halving their segment count is cosmetic.** Every curved geometry in the kit — `buildArchCutout`, `buildCurvedCornerBlock`, `curvedFlatGeo` — is cached in `env.geoCache` by parameter key, so the `ExtrudeGeometry` construction and its per-vertex UV loop run once per unique key for the entire session, not per cell. Working the selection bands out of `structuralMatrix` (sorted descending, `find(roll >= prob)`) puts `CURVED ARCHWAY` at 0.029–0.031, which is **0.2% of wall cells**; `THE COMPRESSION ARCHWAY` is 0.4%. `ROUND ALCOVE` at 5% is the only curved blueprint common enough to matter. The reduction to 8 segments halves the vertex count of shapes that are built once and shared, which is worth having and is not a fix. If sluggishness persists, the honest next step is instrumenting `geoCache` misses and per-chunk draw calls rather than removing features on suspicion.
- **`HINGED DOORWAY` keeps its probability band even though placement is now entirely from the pre-pass.** The obvious move was to raise `prob` out of range so the random roll could never draw it. Measured, that hands its eight points to the next profile down: `NARROW HEADER GAP` goes from 4% to 12% of all wall cells, tripling silently and reshaping the level. The band therefore stays at 0.78 and a random draw with no plan behind it resolves to plain wall instead, leaving every other blueprint's share exactly as it was. The cost is that those cells are plain wall rather than something, and they don't land in `solidWallCells`, so they aren't offered as breaker mounting points.
- **The doorway planner was developed against a simulation that loads its own source, and that simulation found five bugs that syntax checking could not.** In order: `dir` declared inside the facing-search loop but referenced after it (a hard `ReferenceError` on the first door planted); a later plan's seal walling in an earlier door's approach (4,219 cases); a run winding back to seal its own approach (2,827); the terminus landing on the run's own approach (60); and corridors running alongside another door's approach, letting the player walk in beside a door rather than through it (832, then a further 127 when the run's first cell escaped the same check). All five would have shipped as doors sealed into walls or corridors you could sidestep.
- **Two known limits, both deliberate.** Extending a breach crawl or planting a doorway consumes `random()` draws that the previous code didn't, so chunks containing either will generate differently on an existing seed — the same is already true of the artery exclusion. And the merged VAR screen re-renders the whole list on every edit, because an edit can migrate an entry between stores and change its resolved preview, so focus leaves the field after a change.

## [v0.9.0] - 2026-08-09

_The Airlock Autopsy_

### Fixed

- **[ENGINE] The Sector-Load Freeze Screen Never Actually Covered A Sector Load:** `main.js`'s `LOADING SECTOR...` overlay (added in v0.9.1) only engaged while `environment.isBuildingChunk` was true, and that flag is exclusively managed by `processChunkQueue()` — the ordinary chunk-streaming path. A macro sector's actual interior (the geometry inside an Atrium, Archive, Checkpoint, etc.) builds on a separate, deferred path: `ensurePendingContentAtPlayer()` calls `beginMacroChunkContent()` the moment the player's position crosses into the zone's bounds, and that function fires `_buildChunkInterior()` fire-and-forget, entirely outside `isBuildingChunk`'s bookkeeping. Every sector-entry hitch — including the multi-second Atrium spike below — was therefore invisible to the one system built specifically to explain it: the player just froze mid-frame with no loading state, no cursor change, nothing. `beginMacroChunkContent()` now sets a dedicated `environment.isBuildingMacroInterior` flag for the duration of the build, kept separate from `isBuildingChunk` on purpose since the two can legitimately be in flight at once (neighboring chunks streaming in while the player's own sector interior is still building) and sharing one flag would let whichever finished first drop it out from under the other. `main.js`'s freeze condition now also triggers on this flag directly, independent of the door-transition state the original check required — entering a sector's bounds by any means, airlock included, is reason enough to freeze until its content is actually there to stand on. Verified live: the freeze engages within a frame or two of the interior build starting and releases cleanly the moment it resolves.
- **[WORLD] The Atrium's 14 Balcony Tiers Are Gone:** Every Atrium chunk built one full ring of rails and balusters per tier — 14 tiers, 4 sides each, up to ~27 individual balusters per side on the five nearest tiers — entirely inside the single synchronous cell that also caps the shaft with its void-sky plane. That's on the order of 700 individual `THREE.Mesh`/`THREE.Group` objects constructed back-to-back with no yield point the chunk builder's 5ms time-slicing could land on. They were also only ever visible looking straight up through the airlock opening. Removed the tier construction outright; `TIER_BASE`/`TIER_STEP`/`TIER_COUNT`/`TOP_TIER_Y` stay in place since the perimeter wall banding and the sky cap both still key their height off the same shaft scale. Measured contribution to the sector's build time: negligible on its own (the per-cell work profiled at under 50ms total across an entire chunk), but it's 700 fewer objects and non-instanced draw calls for no visual loss most players will ever notice.

### Notes

- **The balcony removal was not, on its own, the fix for the reported spike.** Isolating the deferred interior build directly (bypassing the fire-and-forget wrapper to await and time it in place) traced the real cost to `ChunkManager._compileInstances`: `renderer.compileAsync` isn't available in this project's three.js build, so its fallback always ends in a synchronous `renderer.compile(env.scene, env.camera)` — a full-scene shader compile, not scoped to the new chunk. Re-verifying already-compiled programs against the rest of the scene is cheap (confirmed: re-running `compile()` on an already-warm scene costs ~20ms regardless of scene size); actually linking a brand-new program is not. The Atrium sector lazily creates roughly a dozen distinct canvas-textured materials — vending panel, cart lattice, soup can, product boxes, and more — that no other sector touches, and the first Atrium a seed ever produces has to compile all of their shaders in one synchronous breath. Measured directly: 3.5-10s of main-thread stall on a fresh Atrium's interior build across five separate samples, against 115-460ms for every other sector and 9-50ms for an ordinary chunk (with an unrelated ~2-3s outlier seen twice on ordinary chunks too, at a rate of roughly 2%, that's a separate open question — see below).
- **Pre-building Atrium's materials at boot was tried and measured to not help.** A `prewarmSectorShaders()` pass built one full, real Atrium chunk in reserved, unreachable coordinates during the boot loading screen specifically to force those dozen materials through `compile()` early, then fully evicted it afterward (including from `discoveredSectors`/`_macroChunkHashes`, which normal chunk eviction deliberately never touches — the Compass reads those to keep pointing at sectors that scrolled out of range, so a leftover fake entry there would eventually point a player at a location a million units out). It added a consistent 8-10s to every boot. Re-tested against a genuine, later, real Atrium entry anyway: still a 10s stall. Compiled shader programs in this three.js build are keyed in part by the live light/shadow state at compile time, which is unavoidably different at boot (before a single real frame has run, every pooled light still at its just-constructed default) than mid-playthrough — so the same material still needed a fresh program on first real entry regardless. Chasing an exact match for that state felt like a good way to trade a known, bounded boot delay for an unproven, fragile fix, so the prewarm was pulled in favor of the freeze-screen fix above: it doesn't make the compile faster, but it makes the wait honest, and it covers every sector's first-entry cost, not just Atrium's.
- **A ~2-3 second stall was also observed on plain, non-sector chunks, independent of Atrium, at roughly a 2% rate across several hundred sampled builds in totally different regions of the seed.** Same underlying mechanism suspected — a chunk whose particular roll of blueprints happens to introduce a material combination the scene hasn't compiled yet — but not yet isolated to a specific blueprint. Worth a follow-up pass with the same isolate-and-time approach used here if it turns out to be a frequent enough player complaint on its own.
